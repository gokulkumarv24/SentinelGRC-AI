# Framework and legal content governance

SentinelGRC supports compliance workflows. It does **not** certify, attest, issue audit opinions or give legal advice, and the product says so wherever results could be mistaken for those (dashboards, compliance pages and every report).

The sources, licences and regeneration steps for the bundled content are in [`framework-data/README.md`](../framework-data/README.md). This page sets out the rules the content follows and how the product enforces them.

## Rules

| Rule | How it is enforced |
|---|---|
| Record provenance for every framework version | Manifests must carry the publisher, version, official URL, retrieval date, licence notes and source version. Import validation flags a manifest without a source URL or licence notes, so the importer must confirm they may store the content before proceeding. Provenance is shown on the framework page. |
| Do not reproduce copyrighted standards | For ISO/IEC 27001, ISO/IEC 42001 and SOC 2, only identifiers and short titles or **internal summaries** (marked as such) are stored. NIST and EU texts are reused under their public terms. |
| Never invent identifiers, text, mappings or dates | Manifests are generated by scripts that validate counts against the published source (for example 106 CSF 2.0 subcategories, 72 AI RMF subcategories), or curated by hand with a source for each entry. There is no AI generation of framework content. |
| Mark sample content as illustrative | Control templates and the cross-framework demo mappings load with `isIllustrative = true` and an *Illustrative* badge. Illustrative mappings start `unreviewed`; adopted template mappings start `pending_review`. |
| Separate official text from interpretation | Official text, internal summaries and an organization's own implementation notes are separate fields, labelled in the UI. |
| Versions are immutable, and changes trigger review | Importing the same key and version again is refused. A new version is a new record, and approved mappings on older versions go back to `pending_review` for the reviewer to confirm. |
| Mappings are reviewable assertions | Each mapping has a type (`supports`, `partially_supports`, `related`, `requires_separate_evidence`), a rationale and a confidence. The proposer cannot approve their own mapping. History and audit record every change. Compliance figures exclude rejected mappings and show the number pending review. |
| GDPR and EU AI Act need qualified review | EU AI Act applicability records hold the organization role, a preliminary classification, assumptions, evidence, a review date and a legal-review status, and carry a "Not a legal determination" notice. The obligation schedule is configurable and shows the date it was checked. |
| SOC 2 is readiness, ISO is management-system support | Wording throughout says "readiness tracking" and "evidence collection", never "compliant", "certified" or "attested". |

## Responsibilities

- **Content maintainers** regenerate or curate manifests, spot-check them against the source, and record the retrieval date and licence basis in the pull request.
- **Each organization's GRC manager** reviews mappings, decides applicability and keeps its statement of applicability current.
- **A qualified legal reviewer** confirms GDPR and EU AI Act applicability before anyone relies on it. The app records who reviewed it and when, but does not replace the review.

## Updating content

1. Regenerate or edit the manifest (see `framework-data/README.md`) and bump its version.
2. Run `npm run reference:sync -w services/api` locally. It is idempotent, adds new versions and never edits existing ones.
3. Use the import preview to review the number of mappings that will need re-review.
4. Release normally; the release container runs the reference sync after migrations.

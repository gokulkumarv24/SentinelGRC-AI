# Deploying to Render (free plan)

A free demo deployment: two Render web services (website and API, with the API also running the background jobs), a free **Neon** PostgreSQL database, and free **Backblaze B2** storage for evidence files. For production use, see [DEPLOYMENT.md](DEPLOYMENT.md).

**Free-plan limits:**
- Services sleep after about 15 minutes without visitors, and the first visit afterwards takes about a minute.
- Scheduled jobs (control tests, reminders, scheduled reports) run only while the API is awake.
- Render free instances have **no persistent disk**, which is why evidence files go to B2.

## 1. Database: Neon (free)

1. Sign up at **neon.tech** and create a project named `sentinelgrc`. Pick the **Singapore** region (same as Render) and the newest PostgreSQL version.
2. Under **Connect**, copy two connection strings:
   - the **pooled** one (its host contains `-pooler`), used by the app;
   - the **direct** one (no `-pooler`), used for migrations.
3. Add them to your local `.env`. **Never paste them into chat, tickets or code.**
   ```
   NEON_DATABASE_URL=postgresql://...-pooler.../neondb?sslmode=require
   NEON_DIRECT_URL=postgresql://.../neondb?sslmode=require
   ```

## 2. Evidence storage: Backblaze B2 (free 10 GB)

1. Sign up at **backblaze.com** → B2 Cloud Storage. Create a **private** bucket, e.g. `sentinelgrc-evidence-<random>`.
2. **App Keys** → *Add a New Application Key*, restricted to that bucket with read and write. Note the **keyID** and **applicationKey** (shown once).
3. The bucket page shows the **S3 endpoint**, for example `s3.us-west-004.backblazeb2.com`. The region is the middle part (`us-west-004`).
4. Add them to your local `.env`:
   ```
   B2_ENDPOINT=https://s3.us-west-004.backblazeb2.com
   B2_REGION=us-west-004
   B2_BUCKET=sentinelgrc-evidence-...
   B2_KEY_ID=...
   B2_APP_KEY=...
   ```

## 3. Prepare the database (run locally, once per release)

```bash
npm run build -w services/api
cd services/api
DATABASE_URL="$NEON_DIRECT_URL" npx prisma migrate deploy      # create or upgrade tables
DATABASE_URL="$NEON_DIRECT_URL" node dist/cli/sync-reference.js  # roles, frameworks, templates
```

Then either:
- **Real use:** create the first admin, with `DATABASE_URL="$NEON_DIRECT_URL" node dist/cli/create-admin.js --email … --name … --org-name … --org-slug …`; or
- **Demo:** seed the fictional demo data with evidence stored in B2 (the seed runs locally in demo mode):
  ```bash
  DATABASE_URL="$NEON_DIRECT_URL" STORAGE_BACKEND=s3 S3_ENDPOINT="$B2_ENDPOINT" S3_REGION="$B2_REGION" \
  S3_BUCKET="$B2_BUCKET" S3_ACCESS_KEY_ID_REF=B2_KEY_ID S3_SECRET_ACCESS_KEY_REF=B2_APP_KEY \
  node dist/cli/seed-demo.js
  ```
  Sign-in details go to `var/demo-credentials.txt` on your computer. Each password must be changed at first sign-in.

## 4. Create the services on Render

1. In the Render dashboard: **New → Blueprint**, then connect the GitHub repository `SentinelGRC-AI`. Render reads `render.yaml` and proposes two services, `sentinelgrc-api` and `sentinelgrc-web`.
2. Fill in the values Render asks for (it never shows them in the repository):

   | Service | Variable | Value |
   |---|---|---|
   | api | `DATABASE_URL` | Neon **pooled** string |
   | api | `PUBLIC_APP_URL`, `CORS_ORIGINS` | `https://sentinelgrc-web.onrender.com` (or the web URL Render shows) |
   | api | `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET` | From B2 |
   | api | `SENTINELGRC_S3_KEY_ID`, `SENTINELGRC_S3_SECRET` | B2 keyID and applicationKey |
   | web | `API_BASE_URL` | `https://sentinelgrc-api.onrender.com` (the API URL Render shows) |

   `AUTH_SECRET` is generated by Render automatically.
3. Apply the blueprint. The first Docker builds take several minutes.
4. If Render gave different URLs than above (for example because the names were taken), update `PUBLIC_APP_URL` and `CORS_ORIGINS` on the API, and `API_BASE_URL` on the web service. Then **redeploy the web service**: its API address is compiled in at build time.

## 5. Check it

- `https://<api>.onrender.com/api/v1/health` returns `{"status":"ok"}`.
- Open the website, sign in, upload a small PDF as evidence and download it again (this proves the storage), then generate a report (this proves the background jobs).
- **Audit Log:** the `auth.login_succeeded` event should show **your** IP address. If it shows a Render (`10.x.x.x`) or Cloudflare (`172.64–172.71.x.x`, `104.16–104.31.x.x`, …) address instead, check that `TRUST_PROXY` on the API is `cloudflare` and redeploy; login rate limiting is per visitor IP.
- If uploads or report generation fail, check the API logs for `Object storage upload failed (403 AccessDenied)` or similar: the B2 application key must have **Read and Write** access to the bucket.

## Optional: AI assistant and AI agent with Groq (free)

1. Create a free key at **console.groq.com** → sign in (Google or email) → **API Keys** → **Create API Key**. Copy it once (it starts with `gsk_`); Groq never shows it again. No card is needed.
2. In the API service's environment, set these, then redeploy:
   - `AI_ENABLED=true`
   - `AI_PROVIDER=openai-compatible`
   - `AI_BASE_URL=https://api.groq.com/openai/v1`
   - `AI_MODEL=openai/gpt-oss-120b`
   - `AI_API_KEY=<your gsk_ key>`
   - `AI_DATA_SHARING_APPROVED=true` (only after you accept that redacted record and document text is sent to Groq)
3. Optional: `AI_AGENT_DAILY_TOKEN_BUDGET` (default `150000`) caps what the background agent uses per 24 hours, so it stays inside Groq's free daily limit (about 200,000 tokens for this model). People asking for drafts on demand are not capped by it.
4. Optional backup provider for when Groq's daily limit is reached: `AI_FALLBACK_BASE_URL`, `AI_FALLBACK_MODEL`, `AI_FALLBACK_API_KEY` (any OpenAI-compatible endpoint, for example NVIDIA NIM or OpenRouter).

Note: "Grok" (xAI) is a different, paid service. It also works (`AI_BASE_URL=https://api.x.ai/v1` and its model name), but Groq is the free option.

Then open **AI Agent** in the app: the status should say "Working". See [AI_AGENT.md](AI_AGENT.md) for what each agent job does.

## Updating

Push to `main`, then in Render choose **Manual Deploy** on both services (auto-deploy is off in the blueprint). If the release contains migrations, run step 3's `migrate deploy` command **before** deploying.
